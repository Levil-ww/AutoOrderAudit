2026-08-11 合并订单赠品无限增长问题修复 工作总结
================================================================================

一、问题背景
================================================================================

合并订单 6928601810063031567&6928604049951915279 出现赠品行"无限增长"现象：
每次程序运行都会新增一行相同的赠品行，导致订单中出现 4~6 行重复的赠品。

子订单备注：
- 子订单1 (6928601810063031567): "定制双面革安妮森林;35x320cm-1张，赠品圆垫-1张"
- 子订单2 (6928604049951915279): "赠送赠品圆垫-1张，方垫-1张"（纯赠品备注）

伴随问题：
1. 子订单2（纯赠品备注，解析结果 success=False）的赠品被整体跳过
2. 备注中的"方垫"未被识别为 30x50 赠品（应映射到
   `吸水皮革-标准-30x50-随机发；30x50`）

二、根因分析
================================================================================

1. 反馈循环：ERP 保存赠品行时自动把订单级备注关联到新建的赠品行 shop_remark
   字段。下次运行时，adapter 的 _build_gift_item 在缺少显式 shop_remark 时
   会回退到 order.shop_remark（订单级备注），导致订单级备注中的
   "赠品圆垫-1张" 被反复解析、反复创建赠品行。

2. 纯赠品备注跳过：engine._process_merged_order 在分组解析失败（success=False）
   时直接 continue，未收集该分组的赠品信息，导致子订单2 的圆垫/方垫丢失。

3. 上下文继承缺失：parser._extract_multiple_gifts 只识别带"送/赠品/附赠/加送"
   前缀的赠品。当备注形如 "赠送赠品圆垫-1张，方垫-1张" 时，第二个"方垫"
   没有前缀，导致漏识别。

4. 缺少赠品行去重：adapter 在处理赠品前未对 ERP 已存在的重复赠品行去重，
   导致 ERP 创建的重复赠品行被反复收集、反复匹配。

【改动2】adapters/fangguo/adapter.py —— 阻止赠品行 fallback 到订单级备注
--------------------------------------------------------------------------------
位置：_build_gift_item 方法（约 1816~1820 行）

修改前：
    remark = shop_remark or item.shop_remark or order.shop_remark or ""

修改后：
    # 赠品行不应携带订单级备注，否则 ERP 保存后会把订单级备注关联到赠品行，
    # 导致下次运行时被误解析（形成反馈循环）。
    # 只使用显式传入的 shop_remark 或原商品行自身的 shop_remark，
    # 不回退到 order.shop_remark。
    remark = shop_remark or item.shop_remark or ""

效果：切断"订单级备注 → 赠品行 shop_remark → 再次解析"的反馈循环。


【改动3】adapters/fangguo/adapter.py —— 新增 engine_gifts 参数
--------------------------------------------------------------------------------
位置：update_merchant_code 方法签名与赠品合并逻辑（约 386 行、918~936 行）

方法签名新增参数：
    engine_gifts: list = None
    # engine 层完整收集的赠品 [(name, num, tid), ...]，
    # 用于传递 success=False 分组（纯赠品备注）中的赠品。
    # 若提供则与 parsed_list 中的赠品合并后按 tid 分组去重。

合并逻辑：
- 记录 parsed_list 中已收集的 (name, tid) 集合 existing_pairs
- 遍历 engine_gifts，若 (gname, gtid) 已在 existing_pairs 中则跳过，避免重复累加
- 否则加入 gifts_by_tid[gtid]['gifts']

关键代码片段：
    if engine_gifts:
        existing_pairs = set()
        for tid, info in gifts_by_tid.items():
            for gname, _ in info['gifts']:
                existing_pairs.add((gname, tid))

        for gift_tuple in engine_gifts:
            if len(gift_tuple) >= 3:
                gname, gnum, gtid = gift_tuple[0], gift_tuple[1], gift_tuple[2]
                if (gname, gtid) in existing_pairs:
                    continue
                if gtid not in gifts_by_tid:
                    gifts_by_tid[gtid] = {'gifts': [], 'material_code': '', 'shop_remark': ''}
                gifts_by_tid[gtid]['gifts'].append((gname, gnum))

七、注意事项与后续维护建议
================================================================================

1. 赠品行 shop_remark 来源约束
   - 赠品行的 shop_remark 只能来自显式传入参数或原商品行自身
   - 严禁回退到 order.shop_remark，否则会再次触发反馈循环
   - 后续如需修改 _build_gift_item，务必保留此约束

2. engine_gifts 与 parsed_list 赠品去重
   - adapter 合并时以 (name, tid) 为去重键
   - 若同一 (name, tid) 在两处都出现，以 parsed_list 为准，engine_gifts 跳过
   - 避免同一赠品被重复累加数量

3. 赠品上下文继承的边界
   - 仅当前面已识别到白名单赠品时才触发补充提取
   - 从 last_accepted_match_end 之后开始搜索，避免重复匹配
   - 30x50 数量解析特殊处理：优先匹配 "-数字"，避免把 30 误识别为数量

4. 赠品行去重优先级
   - type=0 原始行 > type=1 手工单行
   - 有 sys_oid 且不以 'new_' 开头 > 其他
   - 同优先级按 idx 升序保留第一个

5. 跨子订单不去重
   - 赠品去重分组键包含 original_tid
   - 不同子订单的相同赠品行不会被互相去重
   - 这是"两个子订单各有圆垫"场景能正确保留的关键
