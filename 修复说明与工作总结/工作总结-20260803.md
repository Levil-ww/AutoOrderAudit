# AutoOrderAudit 工作总结 — 2026-08-03

## 概述

本次工作围绕 **合并订单赠品去重问题** 展开，这是一个涉及多个相互关联 Bug 的严重缺陷。
    用户反馈：合并订单中赠品行被错误去重/删除，导致数量丢失——程序删除了一个赠品行，但未将剩余赠品行的数量修改为 2，属于重大失误。

经深入排查，共发现并修复 **4 个关联 Bug**，涉及 `core/engine.py` 与 `adapters/fangguo/adapter.py` 两个核心文件。修复采用三层防御纵深策略，确保赠品行在任何场景下都不被误删、误改或误合并。

---

## 问题背景

### 用户反馈场景

合并订单包含 2 个子订单：
- 子订单 `6954947999332898654`：系统原有 1 个圆垫赠品行
- 子订单 `6954950281027000158`：备注说明要送方垫 30x50-1 张

**正确行为**：
- 子订单1的圆垫赠品行保持不变（备注无赠品修改说明）
- 子订单2新建一个方垫赠品行（挂子订单2的 `original_tid`）

**实际错误行为**：
- 程序删除了一个赠品行，但未修改剩余赠品行的数量
- 或者将子订单1的圆垫编码直接改成方垫，挂错了子订单号

### 核心规则确立

1. 若订单备注中**无**赠品说明（种类、数量等），则**不修改**系统原本存在的赠品订单行
2. 若备注中**有**赠品说明（如"赠品方垫30x50cm-1张"），则判断是在原赠品行修改还是新建——判断依据是 `original_tid` 是否匹配
3. 合并赠品行时**必须同步调整数量**，不能只删除行而不改数量

## 子问题一：SKU 去重误删不同子订单的相同 SKU

### 背景

`core/engine.py` 中的 SKU 去重逻辑按 `(标准化SKU, 数量)` 分组，当两个不同子订单恰好有相同 SKU 时，会被当作重复项而删除其中一个。这导致后续赠品解析结果缺失，连锁引发赠品行匹配异常。

### 改动

- **文件**：`core/engine.py` L960-L1048
- **修复**：新增 `original_tid` 分组逻辑。当现有商品行包含多个不同 `original_tid` 时，按 tid 分组保留解析结果，仅合并同一子订单内的重复 SKU。
- 具体逻辑：
  1. 获取该 SKU 对应的现有商品行的 `original_tid` 集合
  2. 若 `tid` 集合数量 > 1，说明是不同子订单拥有相同 SKU，按 tid 分组保留候选
  3. 每个 tid 保留一个最优解析结果，不跨 tid 合并

### 结果
- 不同子订单的相同 SKU 不再被误删，每个子订单的解析结果独立保留。

## 子问题二：赠品去重合并了不同子订单的相同赠品

### 背景

`core/engine.py` 中 `all_gifts` 去重使用 `dict.fromkeys(all_gifts)`，赠品元组格式为 `(name, num)`。当两个子订单各有 1 个圆垫赠品时，会被合并成一条记录 `(圆垫, 1)`，导致数量信息丢失（应合并为 `(圆垫, 2)` 或保留两条独立记录）。

### 改动

- **文件**：`core/engine.py` L846-L896
- **修复**：
  1. 将赠品元组从 `(name, num)` 扩展为 `(name, num, tid)`，携带子订单号
  2. 收集赠品时传入 `tid`：`all_gifts.append((gname, gnum, tid))`
  3. 去重时按 `(name, tid)` 合并数量，确保不同子订单的相同赠品不被跨子订单合并

```python
# 修复后：按 (赠品名, tid) 合并数量，不同子订单的赠品不合并
gift_merged = {}
for gname, gnum, gtid in all_gifts:
    key = (gname, gtid)
    if key in gift_merged:
        gift_merged[key] += gnum
    else:
        gift_merged[key] = gnum
all_gifts = [(name, num, gtid) for (name, gtid), num in gift_merged.items()]
```

- 同步修改了所有引用 `all_gifts` 的位置（L1069、L477、L1101），解包从 `(name, num)` 改为 `(name, num, _)`。

### 结果
- 不同子订单的相同赠品（如各 1 个圆垫）不再被合并成 1 条，保留为 2 条独立记录。

## 子问题三：适配器静默丢弃未匹配的赠品行

### 背景

`adapters/fangguo/adapter.py` 中，当 `all_gifts` 条目少于现有赠品行时（如因 Bug1/Bug2 导致解析结果缺失），多余的赠品行被静默丢弃——既没有保留原行，也没有修改数量，直接消失。

### 改动

- **文件**：`adapters/fangguo/adapter.py`（原 L925-L977 区域，已被 Bug4 修复覆盖）
- **修复**：在处理完所有 `all_gifts` 条目后，检查剩余未匹配的赠品行，将其按原样保留或按"赠品不送"规则处理，绝不静默丢弃。

### 结果
- 未被备注赠品说明匹配到的原赠品行，保留原 SKU 和数量不变。

## 子问题四：赠品行按顺序匹配而非按子订单号匹配（最关键）

### 背景

这是本次修复中**最核心的 Bug**。原代码在 `adapters/fangguo/adapter.py` 中按**列表顺序**匹配赠品行：

```python
# 修复前（错误逻辑）：
existing_idx = 0
for gift_name, gift_num, gift_tid, ... in all_gifts:
    if existing_idx < len(existing_gift_indices):
        existing_gift_idx = existing_gift_indices[existing_idx]  # 按顺序取！
        new_gift = self._build_gift_item(order.items[existing_gift_idx], ...)
        existing_idx += 1
```

这意味着：如果 `all_gifts[0]` 是子订单2的方垫，而 `existing_gift_indices[0]` 是子订单1的圆垫，程序会直接在圆垫的商品行上改编码成方垫——子订单1的圆垫被覆盖，方垫还挂错了子订单号。

### 改动

- **文件**：`adapters/fangguo/adapter.py` L908-L1002
- **修复**：将赠品行匹配从"按顺序匹配"改为"按 `original_tid` 精确匹配"

具体逻辑：
1. **收集现有赠品行并按 `original_tid` 分组**：
   ```python
   existing_gifts_by_tid = {}  # {original_tid: [idx, idx...]}
   for idx, item in enumerate(order.items):
       if idx not in used_item_indices and self._is_gift_item(item):
           item_tid = item.original_tid or ""
           existing_gifts_by_tid.setdefault(item_tid, []).append(idx)
   ```

2. **遍历解析赠品时按 tid 精确查找匹配**：
   ```python
   for gift_name, gift_num, gift_tid, ... in all_gifts:
       matched_existing_idx = None
       if gift_tid in existing_gifts_by_tid and existing_gifts_by_tid[gift_tid]:
           matched_existing_idx = existing_gifts_by_tid[gift_tid].pop(0)

       if matched_existing_idx is not None:
           # tid 匹配 → 在原赠品行上修改编码和数量
       else:
           # tid 不匹配 → 新建赠品行（绝不乱改其他子订单的赠品行）
   ```

3. **剩余未匹配的现有赠品行保留原样**：
   - 处理完所有解析赠品后，`existing_gifts_by_tid` 中剩余的赠品行（没有任何备注赠品匹配到它们的 tid）被原样保留

### 场景验证

| 子订单号 | 原赠品行 | 备注赠品说明 | 修复后行为 |
|---------|---------|-------------|-----------|
| ...898654 | 圆垫 | 无说明 | 🔒 保留原样不变 |
| ...000158 | 无 | 方垫30x50-1张 | ➕ 新建方垫赠品行（挂子订单2） |

日志输出标记：
- `🔒 保留原赠品行不变`：无备注说明的赠品行保留
- `➕ 新建赠品行`：备注要求的赠品在对应子订单新建
- `🔧 在原赠品行上修改`：仅当 tid 完全匹配时才修改

### 结果
- 子订单A的赠品行绝对不会被子订单B的赠品覆盖修改
- 备注中有赠品说明但无匹配原赠品行时，正确新建赠品行
- 无备注说明的原赠品行保持原样

## 防御纵深设计

本次修复采用三层防御策略，确保不会因单点故障导致赠品问题：

| 层级 | 位置 | 防御内容 |
|------|------|---------|
| 第一层 | `engine.py` SKU 去重 | 从源头保证每个子订单的商品行解析结果不被误删 |
| 第二层 | `engine.py` 赠品去重 | 确保不同子订单的赠品独立处理，不被跨子订单合并 |
| 第三层 | `adapter.py` 赠品行匹配 | 按 `original_tid` 精确匹配，找不到则新建，剩余保留原样 |

即使前一层出现意外，后一层也能兜底保护赠品行不被误删或误改。

## 经验沉淀

- **合并订单处理必须以 `original_tid` 为锚点**：不能按列表顺序匹配商品行或赠品行，否则跨子订单的覆盖修改是必然结果。
- **去重操作需区分"同子订单内重复"与"不同子订单的相同项"**：前者应合并，后者应独立保留。分组键必须包含 `original_tid`。
- **删除操作必须有数量补偿机制**：删除一个赠品行时，必须同步修改剩余赠品行的数量，不能只删不改。
- **未匹配的现有数据不应静默丢弃**：当解析结果少于现有数据行时，多余的数据行应保留原样，而非丢弃。
- **防御纵深是关联 Bug 修复的最佳策略**：多个 Bug 相互关联时，单点修复容易遗漏，应在数据流经的每一层都加入防御逻辑。
